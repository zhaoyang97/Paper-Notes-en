# Team Anotheroption at SemEval-2025 Task 8: Bridging the Gap Between Open-Source and Proprietary LLMs in Table QA

**Conference**: ACL 2025 (SemEval Workshop)  
**arXiv**: [2506.09657](https://arxiv.org/abs/2506.09657)  
**Code**: [GitHub](https://github.com/Nickolas-option/QA_on_Tabular_Data_SemEval2025_Task8)  
**Area**: LLM / NLP  
**Keywords**: Table QA, Text-to-SQL, Multi-model orchestration, RAG, Open-source LLM

## TL;DR

Proposed a multi-model collaborative pipeline system for Table QA, integrating three paths: Text-to-SQL, Text-to-Code (Pandas), and end-to-end semantic understanding. By leveraging RAG to retrieve and enhance contexts, and employing Llama 3.3-70B as an Orchestrator to adjudicate the final answer, the system achieved a 13/38 ranking with an 80% accuracy in the SemEval-2025 Task 8 open-source track. On the development set, the open-source combination (88%) significantly outperformed the single GPT-4o model (74%).

## Background & Motivation

**Background**: Table QA (Question Answering) maps natural language queries to executable operations on structured data (returning strings, numerical values, booleans, or lists), which is widely applied in finance, healthcare, and business data analysis. Current mainstream solutions are split into two categories: code-generation-based methods (Text-to-SQL/Python) excel at numerical calculations and precise querying, while end-to-end (E2E) direct answering methods excel at semantic understanding queries.

**Limitations of Prior Work**: While proprietary models such as GPT-4o exhibit outstanding performance in Table QA, open-source models have lagged behind for a long time, limiting research reproducibility and deployment flexibility. A single model or single methodology path struggle to cover all query categories—numerical aggregation is suited for SQL/Python, whereas semantic judgments like "whether the title involves communication" are suited for E2E.

**Key Challenge**: Real-world tabular data is highly noisy (missing values, emoji column names, abbreviations, etc.). Code generated by LLMs often suffers from aggregation logic errors, type operation errors, and missing arguments. Meanwhile, E2E methods face a "needle in a haystack" dilemma—injecting the entire table into the context makes it excessively long, causing key information to be missed or hallucinated.

**Goal**: (1) How to coordinate multiple open-source models to bridge the gap with proprietary models? (2) How to achieve complementarity between code generation and semantic understanding? (3) How to handle noise and format mismatch in real-world data?

**Key Insight**: The authors observe that different models and methodological paths possess distinct advantages on various question types. The bottleneck of a single model can be transcended through multi-model voting and orchestration. Instead of pursuing a single, more powerful model, designing an intelligent multi-path pipeline with an arbitration mechanism is more effective.

**Core Idea**: Use multiple open-source LLMs to generate candidate answers through three paths—SQL, Python, and E2E—and then let an Orchestrator select the most reliable one, achieving "wisdom of the crowd" that outperforms a single strong proprietary model.

## Method

### Overall Architecture

The system comprises two major parallel pathways: **Code-based** (SQL + Python) and **End-to-End**. Each path generates candidate answers independently, which are then arbitrated by an Orchestrator (Llama 3.3-70B Instruct) to select the final response. The input consists of a natural language question and tabular data, and the output is a precisely formatted answer (Boolean / Number / Category / List).

### Key Designs

1. **Text-to-SQL Code Generation Module**:

    - **Function**: Translates natural language questions into SQL queries and executes them on an in-memory SQLite database.
    - **Mechanism**: Employs two models, Codestral 20.51 and Qwen Coder 2.5-32B, to generate SQL queries independently. The prompts incorporate relevant row data and recommended column names retrieved via RAG to enrich context. Queries are executed on an in-memory SQLite database via SQLAlchemy, producing one candidate answer.
    - **Design Motivation**: SQL is naturally suited for precise querying and aggregation of structured data, and independent generation by two models introduces beneficial diversity.

2. **Pandas Code Generation Module**:

    - **Function**: Translates natural language questions into Python/Pandas code and executes them in a sandboxed environment.
    - **Mechanism**: Similarly utilizes Codestral and Qwen Coder to generate Python code, which runs inside a sandbox equipped with timeout protection. Execution statuses and error messages are recorded for potential self-correction. Python is more flexible than SQL and can handle complex data transformations and multi-step reasoning.
    - **Design Motivation**: SQL and Python show complementary strengths across different question types—SQL excels at simple aggregation, whereas Python is more fitting for complex data-processing logic. Combining them improves accuracy from 72% to 84%.

3. **RAG Retrieval-Augmented Module**:

    - **Function**: Injects the most relevant table rows into the LLM context to resolve data format mismatches.
    - **Mechanism**: Creates sentence embeddings and indexes them for each relevant column. During query time, the top-3 semantically closest rows are retrieved and injected into the LLM context. For instance, when answering "how many customers are from Japan", RAG informs the model that 'japan' is lowercase in the dataset, preventing case-mismatches.
    - **Design Motivation**: Real-world datasets contain inconsistent casing and formatting variants. Forcing LLMs to guess the format often yields errors; RAG provides concrete data samples as references.

4. **Self-Correction**:

    - **Function**: Automatically passes error messages back to the LLM to regenerate code when SQL/Python execution fails.
    - **Mechanism**: Gathers schema information, error messages, and original questions, and resubmits them to the LLM to generate corrected code. This is inspired by the ReForce framework.
    - **Design Motivation**: Although its practical effect is limited (since at least one of the four code-generation agents usually succeeds), it provides a fallback guarantee in extreme cases.

5. **End-to-End Semantic Understanding Module**:

    - **Function**: Bypasses code generation, allowing the LLM to directly read tabular text to answer the question.
    - **Mechanism**: Uses MiniMax-01 to convert tabular data into Markdown format, which is inputted together with the question into the LLM to directly generate answers. Answers must strictly comply with the designated data type (Boolean/List/Number/String). Context length is constrained by relevant columns selected through RAG.
    - **Design Motivation**: Certain questions require semantic understanding rather than precise calculation, such as determining if a title is related to a topic, or inferring gender from names. E2E methods significantly outperform code generation on such questions.

6. **LLM Orchestrator Arbitration Module**:

    - **Function**: Selects the most likely correct response from multiple candidate answers as the final output.
    - **Mechanism**: Utilizes Llama 3.3-70B Instruct as the orchestrator to receive all successfully executed candidate answers and their associated code, evaluating the plausibility of each candidate based on specific prompt instructions. A key constraint is that the Orchestrator cannot generate new answers and must choose only from existing candidates.
    - **Design Motivation**: Different paths and models fail and succeed on different questions. The Orchestrator simulates "majority voting + logical evaluation" to enhance final accuracy.

### Auxiliary Techniques

- **Column Prediction**: Prompts the LLM to pre-select columns relevant to the question, reducing context length to mitigate the "needle in a haystack" issue for E2E models.
- **Column Renaming**: Renames abbreviated column names to readable forms (e.g., DMC → Duff Moisture Code), aiding the LLM's comprehension of data semantics.
- **Checklist-style Prompt**: Embeds check items (type matching, entity verification, logical consistency, etc.) into the code generation prompt, preventing LLMs from skipping crucial instructions.
- **Emoji Handling**: Replaces emojis in column names with unique hash symbols to prevent exact-match failures caused by LLMs adding or omitting spaces when processing emojis.
- **CoT Reasoning**: Explicitly instructs the LLM to perform detailed reasoning before outputting the final answer, utilizing fuzzy matching to extract the final answer from verbose responses.

### Key Findings

- **Open-Source Combination Beats Proprietary Single Model**: The open-source model combination (88%) outperforms the single GPT-4o model (74%) by 14 percentage points, proving that orchestrating multiple weaker models can yield a "wisdom of the crowd" effect. Applying the same pipeline to GPT-4o boosts its performance from 74% to 87%, indicating that the pipeline architecture itself is highly valuable.
- **Significant SQL Complementary Effect**: Transitioning from "Python only" to "Python + SQL" improves accuracy from 72% to 84%, highlighting that the two code formats complement each other significantly across different question types.
- **Question Reformulation is Counterproductive**: Reformulation degrades accuracy across all configurations (Python: 72% → 68%, E2E: 54% → 52%). This degradation occurs because early errors propagate downstream without recovery mechanisms, whereas multi-model paths already offer implicit "error filtering" through the Orchestrator.
- **Orchestrator Decision Analysis**: 63.4% of decisions are consensus confirmations (all candidates agree), 14.6% filter logically flawed answers, 12.2% reject format-mismatched answers, and 9.8% arbitrate conflicting answers. The Orchestrator played an active role in 36.6% of the cases.
- **Limited Effect of Self-Correction**: Since at least one of the four code generation agents typically produces executable code, self-correction is rarely triggered.

## Highlights & Insights

- **The "Free Lunch" of Multi-Model Orchestration**: By combining two coding models, one E2E model, and an Orchestrator, the open-source pipeline outperforms the proprietary counterpart without any fine-tuning. This demonstrates that for specific tasks, a sound system design can be more critical than model scale.
- **Replaceability of Modular Architecture**: The three paths (SQL, Python, and E2E) are entirely decoupled. Every component can be independently upgraded or replaced without affecting the rest, facilitating continuous improvement.
- **Pipeline is Equally Effective for Strong Models**: GPT-4o's accuracy increases from 74% to 87% upon employing the pipeline, validating that this multi-path + arbitration paradigm is more than a compensation strategy for weaker models; it serves as a general-purpose performance enhancement framework.
- **Value of Negative Findings**: The discovery that question reformulation degrades performance reveals that error propagation dynamics in multi-model pipelines differ drastically from single-model settings—errors introduced early in the pipeline cannot be corrected downstream, whereas multi-path designs inherently provide redundancy.

## Limitations & Future Work

- **Helplessness Against All-Candidate Errors**: When all code generation agents and the E2E module retrieve incorrect answers, the Orchestrator cannot independently generate the correct answer. This represents a fundamental limitation of multi-model orchestration.
- **Semantic Gap in Retrieval**: When the query's terminology diverges significantly from the table data, embedding-based retrieval fails to fully bridge the linguistic gap.
- **Sensitivity to Model Scale**: The system's performance is sensitive to model scale. Utilizing smaller open-source models degrades performance drastically; deployment costs remain high due to requiring a 70B Orchestrator and 32B Coder.
- **Risk of Misinterpretation in Column Renaming**: LLMs can misinterpret abbreviated column names (e.g., GPT-4o explaining "ISI" as "Fire Spread Index" instead of "Initial Spread Index"), requiring additional validation mechanisms.
- **Lack of Dynamic Path Selection**: Currently, all queries pass through all paths. Future iterations could dynamically decide whether code execution or semantic analysis is required based on question characteristics to improve efficiency.

## Related Work & Insights

- **vs TeleAI (1st place, 95%)**: The top-ranked solution likely utilized more detailed prompt engineering or stronger model ensembles. The ~15% gap suggests ample room for improvement, particularly in code generation quality and complex reasoning.
- **vs ReForce (Text-to-SQL Self-Correction)**: The self-correction mechanism in this work is directly inspired by ReForce. However, its effectiveness is diluted by "redundancy" in multi-agent scenarios; self-correction becomes more critical if only a single agent is used.
- **vs DataBench Original Evaluation**: DataBench retains real-world noise (emojis, missing values, abbreviated column names), presenting more challenges than sanitized benchmarks. The emoji-handling and column-renaming strategies of this work are highly transferable to other Table QA systems.
- **Insights**: The paradigm of multi-model orchestration + Orchestrator arbitration can be generalized to other code-generation tasks (e.g., data analysis, report generation) to improve system robustness without fine-tuning.
