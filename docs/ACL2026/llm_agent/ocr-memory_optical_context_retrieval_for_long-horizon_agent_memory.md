# OCR-Memory: Optical Context Retrieval for Long-Horizon Agent Memory

**Conference**: ACL 2026  
**arXiv**: [2604.26622](https://arxiv.org/abs/2604.26622)  
**Code**: Not public (no link provided in the paper)  
**Area**: LLM Agent / Long-term Memory  
**Keywords**: Optical Context Compression, Agent Memory, Visual Retrieval, Long Context, Set-of-Mark  

## TL;DR
OCR-Memory renders long-horizon Agent interaction trajectories into images with numbered anchors. A fine-tuned OCR retriever first locates relevant segments in visual space and then retrieves the original text by index. This preserves complete history under strict context budgets and improves performance on long-range tasks in Mind2Web and AppWorld.

## Background & Motivation
**Background**: LLM Agents are evolving from single-round QA to long-term interaction systems, such as web operations, mobile app navigation, tool calling, and continuous task processing. The capability of such systems depends not only on current reasoning but also on the ability to reuse failure causes, operation paths, tool feedbacks, and environment states accumulated in past episodes.

**Limitations of Prior Work**: The most direct approach is placing historical trajectories into external memory and then stuffing relevant content back into the prompt via text retrieval or summarization. However, raw trajectories often contain massive intermediate reasoning, actions, web structures, API returns, and error messages; saving them in full consumes excessive tokens. While summarization and skill abstraction save tokens, they easily lose precise fields, temporal relationships, and low-level details. Once a task requires looking back at a specific button, error, parameter name, or multi-step causal chain from an old step, compressed text memory proves too coarse.

**Key Challenge**: Long-term Agent memory requires both "high capacity" and "high fidelity." Text context window limits force a choice: either retain massive raw history that cannot fit in the prompt, or compress history at the expense of detail. Traditional RAG also encounters semantically similar but logically irrelevant snippets, while generative memory retrieval may hallucinate vague histories into plausible but non-existent evidence.

**Goal**: The authors aim to construct a long-term memory module that can store arbitrarily long trajectories, consume minimal context budget during retrieval, and ensure the evidence provided to the main Agent is original-level, traceable, and low-hallucination. The problem is decomposed into three sub-problems: how to store trajectories with high density, how to find relevant segments from compressed representations, and how to recover found segments into trustworthy text.

**Key Insight**: The paper borrows the "optical context compression" observation from models like DeepSeek-OCR: dense text can be rendered into images and then input to the model as a relatively small number of visual tokens. Here, the image is not for the Agent to "see" the scene but serves as a high-density long-term memory medium. If the visual model is only responsible for locating relevant regions rather than generating the final text, "visual localization" can be decoupled from "evidence retrieval."

**Core Idea**: Replace pure text memory with image memory containing visual anchors. The model outputs relevant segment indices, and the system deterministically retrieves the original text from external logs, trading visual compression for larger effective memory capacity.

## Method
The core of OCR-Memory is not having the main Agent directly read all historical images, but placing a specialized optical retriever alongside the main Agent. This retriever performs one task: given the current task query and historical trajectory images, it determines which numbered segments might be useful. The content actually injected into the main Agent's prompt remains text, but this text is not generated by the visual model; it is verbatim evidence retrieved from original logs based on indices.

### Overall Architecture
The system maintains an external memory bank where each item contains three parts: an image rendered from a historical trajectory chunk, the original text segments corresponding to each numbered block in the image, and metadata like timestamps and episode IDs. After an episode ends, the system segments user inputs, Agent reasoning, tool calls, tool returns, and environment feedback, assigns a unique number to each segment, and marks them with red bounding boxes and numbers on the image.

When a new task arrives, instead of stuffing all historical text into the main Agent, OCR-Memory inputs the current query and historical images into a DeepSeek-OCR style retrieval model. The model outputs a relevance probability or binary label for each numbered block in each memory image. The system selects segments based on thresholds and Top-K rules. Finally, the `Fetch` operation returns to external logs based on these indices, concatenates the raw text evidence, and injects it into the main Agent's prompt.

This workflow splits Agent memory into two layers: the image layer handles large-scale scanning with low token costs, while the text log layer handles high-fidelity evidence recovery. The main Agent sees precisely retrieved text context rather than freely generated summaries from an OCR model.

### Key Designs
1.  **Locate-and-Transcribe Visual Index Retrieval**:
    - **Function**: Transitions historical retrieval from "generating relevant text" to "selecting relevant indices," reducing hallucinations and long-sequence decoding costs.
    - **Mechanism**: Each memory item is represented as $m_i=(I_i,\{s_{i,k}\}_{k=1}^{K_i},\pi_i)$, where $I_i$ is the trajectory image with numbers, and $s_{i,k}$ is the original text for the $k$-th number. The retrieval model outputs a binary vector indicating relevance for each segment, yielding an index set $\hat{S}(q)=\{(i,k)\mid \hat{y}_{i,k}=1\}$, followed by `Fetch` to retrieve $s_{i,k}$.
    - **Design Motivation**: Visual models are prone to errors when transcribing low-resolution images directly and may semantically complete non-existent information. Restricting the model to output 0/1 or indices constrains the task to verifiable pointer selection, with final text deterministically returned by the database.

2.  **Recall-Prioritized Scoring and Selection Rules**:
    - **Function**: Reduces the risk of missing relevant evidence, making memory retrieval more suitable for Agent decision-making.
    - **Mechanism**: Although the model generates binary labels, the authors do not rely solely on greedy output during inference. Instead, they read the logits for "1" and "0" tokens to calculate $p_{i,k}=\exp z_{i,k}(1)/(\exp z_{i,k}(1)+\exp z_{i,k}(0))$. A low threshold $\tau=0.4$ is used, with a Top-K=5 fallback when no high-confidence segments exist; the total retrieved segment limit is 20.
    - **Design Motivation**: In long-term Agent tasks, missing critical history is often more fatal than providing some irrelevant snippets. This rule explicitly favors recall, allowing the retriever to preserve minimal historical clues even when uncertain.

3.  **Multi-resolution Memory Aging and Proactive Recall**:
    - **Function**: Saves older history using low-resolution images to reduce visual token costs; restores to high resolution when old memory is hit for subsequent access.
    - **Mechanism**: The most recent 5 interaction steps use 1024×1024 high resolution, while earlier history is reduced to 512×512, corresponding to DeepSeek-OCR visual token budgets of approximately 256 and 64 respectively. If low-resolution memory is retrieved, the system re-renders a high-resolution version from original logs and maintains high fidelity for the remainder of the episode.
    - **Design Motivation**: Most old history only needs semantic outlines; only the few reactivated histories require detail. This design turns "memory decay" into an adaptive compression strategy, balancing capacity and readability.

### Loss & Training
OCR-Memory is built on DeepSeek-OCR 3B, but the original model is better at transcription than "finding supporting segments based on questions." Thus, the authors transformed HotpotQA into a visual retrieval dataset: candidate paragraphs for each question were rendered as numbered images, text answers were discarded, and paragraph indices of supporting facts were used to construct binary labels.

The training objective is weighted binary cross-entropy. Since relevant segments are much fewer than irrelevant ones, the authors set the positive sample weight higher than the negative weight (specifically $w_+=2.0$, $w_-=1.0$) to penalize misses at the loss level. The vision encoder was frozen during training, with LoRA applied only to the language decoder (q_proj, k_proj, v_proj, o_proj) with rank 16, alpha 32, and dropout 0.05.

Regarding hyperparameters, the model was trained on the HotpotQA distractor split for 3 epochs using the AdamW optimizer with a peak learning rate of $1e^{-5}$, 10% warmup, global batch size of 128, and gradient clipping at 1.0. To match inference resolutions, a resolution curriculum was added: 1024×1024 and 512×512 resolutions were sampled with probabilities $[0.3, 0.7]$, training the model to perform index selection on both clear and blurry thumbnails.

The main Agent is decoupled from the memory module. The default main reasoning model is GPT-4 with temperature 0; subsequent generalization experiments replaced it with Qwen3-32B to verify that gains stem from the memory mechanism rather than a specific reasoning model.

## Key Experimental Results

### Main Results
The authors evaluated long-term Agent memory on Mind2Web Cross-Task split and AppWorld. Mind2Web reports Element Accuracy, Action F1, Step Success Rate (SR), and Task SR; AppWorld reports success rates across difficulties. All memory methods were constrained by a 4096-token context budget.

| Method | Mind2Web Ele Acc | Mind2Web F1 | Mind2Web Step SR | Mind2Web Task SR | AppWorld Easy | AppWorld Med | AppWorld Hard | AppWorld Avg |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| Zero-Shot | 40.1 | 46.2 | 37.9 | 2.2 | 68.7 | 36.2 | 20.9 | 41.9 |
| Text Retrieval | 41.3 | 48.2 | 38.9 | 2.7 | 72.5 | 44.8 | 21.4 | 46.2 |
| MemoryBank | 43.8 | 49.5 | 39.2 | 3.3 | 81.3 | 50.1 | 24.9 | 52.1 |
| AWM | 49.1 | 55.7 | 42.6 | 4.3 | 84.1 | 53.6 | 27.2 | 55.0 |
| ACON | 48.2 | 54.1 | 41.4 | 4.1 | 84.8 | 55.1 | 28.7 | 56.2 |
| **OCR-Memory** | **53.8** | **59.2** | **46.1** | **4.8** | **86.2** | **57.4** | **30.8** | **58.1** |

OCR-Memory outperformed both text retrieval and existing memory systems on both benchmarks. On Mind2Web, compared to AWM, Element Acc improved from 49.1 to 53.8, and Step SR from 42.6 to 46.1. On AppWorld, the advantage was most significant in the Hard subset: OCR-Memory achieved 30.8, compared to 21.4 for Text Retrieval and 27.2 for AWM. This indicates that visual compression does more than save tokens; it actively helps the system regain access to complex historical details.

### Ablation Study
First, the Set-of-Mark (SoM) mechanism was examined. The authors compared the full method against variants directly generating relevant text and variants predicting bounding boxes.

| Configuration | Ele Acc | Step SR | Retrieval Latency | Description |
| :--- | :--- | :--- | :--- | :--- |
| **OCR-Memory Full** | **53.8** | **46.1** | **1.7s** | With SoM, outputs indices and retrieves raw text |
| w/o SoM (Text Gen) | 46.5 | 39.2 | 5.3s | Model generates text; more hallucinations/slower |
| w/o SoM (BBox) | 49.2 | 44.5 | 2.1s | Predicting boxes is faster but less precise |

This ablation is critical. Without SoM, the model reverts to free generation or unstable spatial boxes. Numbered anchors transform image retrieval into list-based evidence selection, simultaneously improving accuracy and latency.

Multi-resolution proactive recall experiments show that dynamic compression is more stable than fixed low resolution and more token-efficient than fixed high resolution.

| Resolution Strategy | Step SR | Task SR | Avg Visual Tokens/Frame | Description |
| :--- | :--- | :--- | :--- | :--- |
| Static Low-Res (512×512) | 39.7 | 2.9 | 65 | Most efficient but loses semantic details |
| Static High-Res (1024×1024) | 46.5 | 4.9 | 256 | High performance but high long-term cost |
| **Dynamic (Ours)** | **46.1** | **4.8** | **82** | High-res performance at near low-res cost |

### Key Findings
-   **SoM numbered anchors** are the core engineering design; they relieve the visual model of "writing evidence" and focus it on "finding evidence."
-   The value of the **multi-resolution mechanism** lies in the cost curve rather than peak scores; the dynamic strategy uses 82 visual tokens to achieve success rates near the 256-token high-resolution setting.
-   OCR-Memory has a greater advantage as the **token budget** tightens; the paper reports superiority over Text-RAG across 1024 to 8192 tokens, proving it addresses context bottlenecks rather than just model capacity.
-   Gains persist after switching to **Qwen3-32B**: Text Retrieval Ele Acc/Step SR/Task SR were 35.2 / 31.5 / 1.8, while OCR-Memory achieved 48.6 / 42.3 / 3.9.
-   The system explicitly **trades disk space, rendering, and visual retrieval latency** for savings in main inference context tokens.

## Highlights & Insights
-   Using "images" as a compression medium for Agent history rather than traditional environmental observations is a novel pivot that turns visual tokens into capacity extensions for long-term text memory.
-   The **Locate-and-Transcribe** design is clean: localization is handled by neural models, while transcription is handled by a deterministic database. This leverages VLM/OCR understanding while avoiding free-generation hallucinations during evidence recovery.
-   The evaluation goes beyond the "compression ratio" metric, reporting task success, retrieval-level Recall/MRR, evidence fidelity, latency, and storage costs. This reflects the multi-resource trade-offs required for real-world deployment.
-   The proactive recall mechanism provides a natural state management for long-term memory: old memories are stored blurs and become clear once hit. This could be transferred to text summaries or vector stores.

## Limitations & Future Work
-   Requires fine-tuning a specialized **optical retriever**; initial training costs are higher compared to training-free BM25 or dense retrieval.
-   Rendering logs as images incurs **computational overhead** and significantly increases disk usage (1.47MB per episode vs. 18KB for Text-RAG).
-   Requires maintaining DeepSeek-OCR parameters; if the main Agent is already large, this adds memory and engineering complexity.
-   Relies on **rendering quality** and anchor readability. Small fonts in long tables or complex code diffs might still lose cues in 512×512 thumbnails.
-   Current **aging strategies** are simple; finer-grained strategies could be learned based on task importance or failure frequency.
-   **Privacy and security** merit research, as history images are harder to partially redact than text logs.

## Related Work & Insights
-   **vs Text-RAG**: Text-RAG uses vector similarity for text snippets (fast/simple); OCR-Memory scans history as images first, making it more robust under long histories and tight token budgets.
-   **vs MemoryBank**: MemoryBank focuses on summaries for user preferences; OCR-Memory focuses on fine-grained evidence recovery for complex operation tracing.
-   **vs AWM**: AWM abstracts history into workflows; OCR-Memory retains raw evidence, excelling when tasks depend on specific UI elements or API return details.
-   **vs DeepSeek-OCR**: DeepSeek-OCR proved optical context compression's feasibility; this work adapts it for Agent memory with SoM and HotpotQA fine-tuning.
