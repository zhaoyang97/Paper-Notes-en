# Tree-of-Code: A Tree-Structured Exploring Framework for End-to-End Code Generation

**Conference**: ACL 2025  
**arXiv**: [2412.15305](https://arxiv.org/abs/2412.15305)  
**Code**: Unreleased  
**Area**: Code Intelligence  
**Keywords**: Code Generation, Tree Search, LLM Agent, Tool Call, End-to-End Inference, Self-Supervised  

## TL;DR

The Tree-of-Code (ToC) framework is proposed, which organizes end-to-end full code program (CodeProgram) nodes in a tree structure. Combined with an execution-result-based reflection mechanism and randomized prompt/model exploration strategies, it achieves nearly 20% higher accuracy on complex tasks compared to CodeAct with less than 1/4 of the interaction turns, under zero-shot settings without annotated data.

## Background & Motivation

Code as the action space of LLM Agents has shown great potential for handling complex tasks, with CodeAct being a representative work that utilizes code blocks as the action units of agents. However, CodeAct suffers from four key limitations:

**Dependence on Ground Truth Termination**: CodeAct assumes that ground truth is known and can be used to match termination conditions, which is infeasible in actual online scenarios.

**Inefficient Fragmented Thinking**: Generating code blocks step-by-step leads to a fragmented logic chain. As turns increase, repeatedly integrating historical contexts triggers context overload and hallucination accumulation.

**Lack of Multi-path Exploration**: Interacting only along a single reasoning path prevents exploring multiple problem-solving strategies.

**Difficulty in Reusing Trajectory Data**: Trajectories generated by multi-turn interactions cannot be directly combined into complete programs for SFT, and due to the lack of process supervision, they are not suitable for reinforcement learning.

Key Challenge: Since intermediate state supervision signals are hard to obtain, is it possible to treat each end-to-end complete execution as an atomic state? By exploring multiple feasible solutions in parallel and voting for the best, the dependence on intermediate process annotations can be avoided.

## Method

### 1. CodeProgram: End-to-End Code Generation Paradigm

The core innovation of ToC is to define each node in the tree as a **CodeProgram**—generating the complete code program to solve the entire task in one go, rather than generating single actions step-by-step like CodeAct.

Specific process:
- LLM first performs Global Reasoning to analyze and decompose the problem.
- Then it generates end-to-end code containing the complete reasoning logic.
- Thought and code are encapsulated with `<thought>` and `<execute>` tags respectively.
- The success/failure of code execution serves as the sole process supervision signal.

One turn of CodeProgram is equivalent to multiple turns of CodeAct, significantly improving efficiency. Code itself is both a reasoning carrier (code-as-reasoning) and an executable validator.

### 2. Two Auxiliary Tools

To maintain the coherence of the end-to-end pipeline, two auxiliary functions are introduced:
- **res_handler**: A general result handler that generates the required final summary after all tool calls are completed.
- **next_action**: Dedicated to web browsing tasks, deciding the next browsing action based on page content, visited URLs, and the task query.

### 3. Tree Structure and Self-Growth Mechanism

ToC is formulated as $\mathbf{T} = (\mathbf{N}, \mathbf{S})$, where $\mathbf{N}$ is the set of nodes and $\mathbf{S}$ represents the stems (reflective reasoning processes) connecting the nodes.

**Tree Expansion Rules**:
- Adopts Breadth-First Search (BFS), where each parent node branches into $M=3$ child nodes.
- Node growth depends on its own execution state: stopped and collected if execution succeeds; continues to grow if execution fails.
- Maximum depth is $L=3$.

**Execution-based Reflection**: When execution fails, the error message is fed back to the LLM for self-reflection and code correction, generating new nodes in the next layer. The reflection process utilizes the full history (thoughts, code, execution results) of ancestor nodes.

### 4. Exploration Strategy: Prompt Pool + Model Pool

To enhance solution diversity, drawing inspiration from random forests:
- **Model Exploration**: Randomly sample from 10 LLMs, with a uniform temperature of 0.1.
- **Prompt Exploration**: Randomly select from a carefully designed prompt pool. The prompt pool construction includes: using 10 LLMs to evolve 10 diverse prompts from a root prompt, manually filtering 6, and then applying format adjustments, example additions, component reorderings, etc.

### 5. Final Result Generation

Collect the outputs of all successfully executed nodes, and determine the final answer through majority vote and summarization.

## Key Experimental Results

### Table 1: Overall comparison of ToC vs CodeAct vs ReAct

| Method | M3 Average Turns | M3 Accuracy | M3 Output Words | API-Bank L3 Average Turns | API-Bank L3 Accuracy | API-Bank L3 Output Words |
|------|-----------|----------|------------|-------------------|-------------------|---------------------|
| ReAct | 8.2 | 38.1% | 1.86k | 9.5 | 8.2% | 1.66k |
| CodeAct | 7.0 | 49.4% | 1.91k | 8.9 | 19.2% | 1.82k |
| **ToC (3-3)** | **1.7** | **67.1%** | **0.44k** | **2.1** | **38.0%** | **0.39k** |

ToC achieves about 20% accuracy gain on both datasets with less than 1/4 of the interaction turns and output word count.

Key Findings: Single-turn CodeProgram (ToC 1-1) already outperforms multi-turn CodeAct on some models, and the average accuracy further exceeds CodeAct after adding prompt exploration (ToC 1-3). claude-3-5-sonnet performs best in ToC due to its strong instruction-following capabilities.

## Key Findings

- The end-to-end paradigm of CodeProgram shifts the task granularity from "action-level" to "program-level", matching or even surpassing multi-turn interaction methods in a single turn.
- Prompt diversity contributes more to performance than model diversity, and is particularly prominent in fixed-model settings.
- Tree breadth (exploring more independent solutions) is more important than depth (iterative reflection and correction).
- Among the five types of tasks in M3, ToC achieves near-perfect accuracy on all tasks except web browsing.
- The best model for different baseline methods varies by dataset—GPT-4 is best on M3 and GPT-4o on API-Bank for CodeAct, while claude-3-5-sonnet is consistently optimal for ToC.

## Highlights & Insights

- **End-to-End Self-Supervision**: Relies solely on code execution success/failure as the supervision signal, completely avoiding dependence on GT annotations, making it highly suitable for real online scenarios.
- **Win-win in Efficiency and Performance**: Achieves nearly 20% accuracy gain with less than 1/4 of the turns and words, substantially reducing API call costs.
- **Random Forest-style Exploration**: The randomized combination strategy of prompt pool + model pool is simple yet effective, introducing structured diversity to agent systems.
- **General Framework Design**: The tree structure can flexibly integrate any reflection method, and the data generated by CodeProgram can be directly used for subsequent SFT/ReFT training.
- **Extensive Validation**: Conducted comprehensive evaluations using 10 mainstream zero-shot LLMs on two datasets (M3ToolEval, API-Bank level-3).

## Limitations & Future Work

1. **Not Suitable for Fully Open Exploration Scenarios**: For tasks requiring step-by-step perception like robot navigation in unknown environments, complete solutions cannot be generated in one go.
2. **Basic Reflection Mechanism**: Relies only on execution feedback, without exploring finer search strategies (e.g., adaptive pruning, MCTS).
3. **Preliminary Prompt Pool Design**: Mainly relies on simple prompt evolution and manual adjustments, lacking a systematic methodology for prompt pool construction.
4. **Limited Tree Scale**: Defaults to a $3 \times 3$ tree; the effectiveness-efficiency trade-off for larger scales remains to be thoroughly studied.
5. **Limited Dataset Scale**: Only 82 tasks for M3 and 50 tasks for API-Bank level-3, which represents a relatively small validation scale.
6. **Integration with Fine-Tuning Unexplored**: Although discussing that CodeProgram data can be used for SFT/ReFT, actual training experiments have not been conducted.

## Related Work & Insights

| Method | Type | Granularity | Requires GT | Multi-path Exploration | End-to-End |
|------|------|------|--------|-----------|--------|
| ReAct | Reasoning + Action | Action-level | Yes | ✗ | ✗ |
| CodeAct | Code as Action | Code-block-level | Yes | ✗ | ✗ |
| Tree-of-Thoughts | Tree of Thoughts | Thought-level | No | ✓ (Within same solution) | ✗ |
| CodeTree | Multi-agent tree search | Code-level | No | ✓ | ✗ |
| Self-Repair Trees | Repair tree | Program-level | Yes | ✓ | ✗ |
| MCTS Methods | Monte Carlo Tree Search | Step-level | Yes | ✓ | ✗ |
| **ToC (Ours)** | **Self-growing tree** | **Program-level** | **No** | **✓ (Across solutions)** | **✓** |

ToC is similar in name to ToT but different in meaning—ToT explores different thought steps within the same problem-solving path, while ToC explores multiple completely independent full program solutions. ToC is closer to the concept of a "Code Random Forest".
