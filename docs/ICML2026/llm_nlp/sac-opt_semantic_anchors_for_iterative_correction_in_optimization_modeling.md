# SAC-Opt: Semantic Anchors for Iterative Correction in Optimization Modeling

**Conference**: ICML2026  
**arXiv**: [2510.05115](https://arxiv.org/abs/2510.05115)  
**Code**: https://github.com/Forrest-Stone/SAC-Opt  
**Area**: Code Intelligence / LLM Optimization Modeling / Self-consistent Correction  
**Keywords**: Optimization modeling, Semantic anchors, Reverse correction, Solver code generation, LLM Agent

## TL;DR
SAC-Opt "back-translates" LLM-generated optimization solver code into structured semantic anchors (constraints and objectives), compares them line-by-line with the anchors from the original problem description, and iteratively rewrites only the inconsistent constraints/objectives until full alignment. It achieves an average improvement of 7.7% across seven public datasets and a 21.9% improvement on ComplexLP.

## Background & Motivation

**Background**: Utilizing LLMs to translate natural language descriptions of optimization problems (linear programming, integer programming, etc.) into executable Gurobi/CPLEX code is a mainstream path to lowering the barrier to entry for operations research. Representative works include CoE, CAFA, and the OptiMUS series, which generally follow a "one-shot forward generation + post-processing based on solver error messages" methodology.

**Limitations of Prior Work**: Solvers can only check for syntax and feasibility; they **cannot detect semantic errors**. For example, if an upper-bound constraint that should be $\le$ is written as a lower-bound $\ge$, the code will still run and produce an "optimal solution," but this solution has no relation to the original problem. The paper refers to such failures as "silent semantic errors"—they do not throw exceptions, and traditional Reflexion-style "debug based on error messages" cannot capture them at all.

**Key Challenge**: There is an information gap between solver-driven feedback signals (execution errors, infeasibility) and the desired goal of "whether the code faithfully expresses the problem intent." Relying on a solver for signals is essentially asking an executor that does not understand the business logic to verify it, which is inherently impossible.

**Goal**: (1) Proactively detect semantic errors in code without relying on solver feedback or additional training; (2) Enable "fine-grained" correction—avoiding regenerating the entire model each time by only modifying the specific erroneous constraint or objective; (3) Provide a convergent iterative process rather than an infinite loop of guessing.

**Key Insight**: The authors observe that since a problem description can be extracted by an LLM into structured $(\mathcal{P}, \mathcal{V}, \mathcal{C}, \mathcal{O})$ (parameters, variables, constraints, objectives), an agent can conversely "translate" the generated code back into structured anchors $\widehat{S}_{\mathrm{sem}}$ of the same format. By using the same schema for both sets of structured data, they can be aligned, diagnosed, and repaired item-by-item.

**Core Idea**: Use "semantic anchors" as a bidirectional bridge to construct an "extract → translate → reconstruct → verify → re-translate" reverse closed-loop, transforming code generation from an open-loop forward pipeline into a closed-loop semantic alignment process.

## Method

### Overall Architecture
SAC-Opt decomposes the overall LLM optimization modeling into six phases:

1.  **Structured Data Extraction**: An `extract` agent extracts the natural language problem $P$ into a JSON structure $S = (\mathcal{P}, \mathcal{V}, \mathcal{C}, \mathcal{O})$.
2.  **Structured Data → Model Translation**: Split into a simple part $S_{\mathrm{simp}} = \{\mathcal{P}, \mathcal{V}\}$ (handled by template rendering) and a semantic part $S_{\mathrm{sem}} = \{\mathcal{C}, \mathcal{O}\}$ (generated by a `trans` agent) to obtain initial code $\mathcal{M}^{(0)} = \mathcal{M}_{\mathrm{simp}} + \mathcal{M}_{\mathrm{sem}}^{(0)}$.
3.  **Model → Structured Data Reconstruction**: A `recons` agent back-translates $\mathcal{M}_{\mathrm{sem}}^{(t)}$ into structured anchors $\widehat{S}_{\mathrm{sem}}^{(t)}$.
4.  **Semantic Consistency Verification**: Use $\delta(s_i, \widehat{s}_i)$ for item-by-item comparison to identify the error set $\mathcal{E}^{(t)} = \{s_i : \delta=0\}$.
5.  **Iterative Correction**: Rewrite only those items in $\mathcal{E}^{(t)}$, return to step 3 for further verification until $\mathcal{E} = \emptyset$ or $T_{\max} = 5$ is reached.
6.  **Model Debugging**: Assemble the complete code and run it in Gurobi; if execution errors occur, repair the code using Reflexion-style feedback based on error messages (up to 3 times).

The key to the pipeline lies in decoupling "semantic-level correction" (steps 3-5) from "syntax-level correction" (step 6): the former is driven by structured anchors, while the latter is driven by solver error messages.

### Key Designs

1.  **Simple/Semantic Separation and Templated Rendering of Structured Data**:
    *   **Function**: Splits $S$ into $S_{\mathrm{simp}} = \{\mathcal{P}, \mathcal{V}\}$ and $S_{\mathrm{sem}} = \{\mathcal{C}, \mathcal{O}\}$. The former uses a deterministic template $f_{\mathrm{det}}^{\mathrm{trans}}$ (e.g., `RollWidth = data["RollWidth"]`), while the latter is generated by a `trans` agent using an LLM.
    *   **Mechanism**: Parameter and variable declarations are almost "formatted outputs" that do not require language understanding. Using templates eliminates randomness and narrows the error surface to only constraints and objectives. Since constraints and objectives carry the actual business logic and require LLM reasoning, the correction effort is focused entirely on $S_{\mathrm{sem}}$.
    *   **Design Motivation**: By making this cut, subsequent reconstruction and verification only target $\mathcal{M}_{\mathrm{sem}}$, significantly shrinking the state space while preventing "cascading pollution" where fixing a constraint accidentally breaks a variable declaration.

2.  **Model → Structured Data Reconstruction: Semantic Reverse Reconstruction**:
    *   **Function**: Uses an independent `recons` agent to translate the generated solver code $\mathcal{M}_{\mathrm{sem}}$ back into a structured description $\widehat{S}_{\mathrm{sem}} = f_{\mathrm{agent}}^{\mathrm{recons}}(\mathcal{M}_{\mathrm{sem}})$ **using the same schema as the original anchors**.
    *   **Mechanism**: Essentially forces a "code reader" to re-articulate exactly what the code does using the problem's original language. If the implementation is wrong (e.g., writing $\le$ instead of $\ge$), $\widehat{s}_i$ will naturally differ from $s_i$; if correct, they should be semantically equivalent. This step is the "signal source" for the entire reverse closed-loop.
    *   **Design Motivation**: Traditional methods only take solver error messages as feedback, which is akin to "guessing the disease by symptoms." This approach allows the model to "self-report the condition," providing a proxy supervisory signal that can be compared item-by-item without a ground truth solution.

3.  **Anchor-level Consistency Verification + Mismatch-only Iterative Convergence**:
    *   **Function**: Defines a binary consistency function $\delta(s_i, \widehat{s}_i) \in \{0,1\}$ with two implementations: LLM-based (`verif` agent judges equivalence) and Similarity-based (SentenceTransformer calculates cosine similarity with threshold $\tau=0.75$). In each round, the error set $\mathcal{E}^{(t)}$ is computed, and **only the anchors in $\mathcal{E}^{(t)}$** are rewritten via $\mathcal{M}_{\mathrm{sem}}^{(t+1)}[s_i] \leftarrow f_{\mathrm{agent}}^{\mathrm{trans}}(s_i)$.
    *   **Mechanism**: Defines convergence by the monotonic decrease of $|\mathcal{E}^{(t)}|$—since each round either eliminates inconsistencies or stays the same, the loop stops after at most $T_{\max}=5$ rounds. The two verifiers serve as fallbacks: the LLM verifier is accurate but expensive, while the similarity verifier is coarse but can run offline.
    *   **Design Motivation**: Fine-grained incremental correction avoids global regressions (where fixing A breaks B), a typical issue with full-text LLM rewriting. It also binds verification and correction to the same schema, making the loop definable, observable, and terminable.

### Loss & Training
**No training involved**. The entire framework is completely training-free / supervision-free. All four agents (extract / trans / recons / verif) are prompted roles of the same backbone LLM (GPT-4o by default). Key hyperparameters: $T_{\max} = 5$ (semantic correction rounds), debugging rounds $= 3$ (solver retry attempts), similarity threshold $\tau = 0.75$. This "zero training + pure prompt scheduling" is a major selling point—it remains effective when swapped with open-source models like Qwen2.5-72B-Instruct.

## Key Experimental Results

### Main Results

Backbone = GPT-4o, Verifier = LLM-based, average of 5 runs across 7 datasets:

| Dataset | SAC-Opt | Runner-up (OptiMUS-0.3) | Gain |
| :--- | :---: | :---: | :---: |
| NL4OPT | 86.8% | 79.8% | +7.0% |
| IndustryOR | 63.8% | 54.3% | +9.5% |
| EasyLP | 96.5% | 92.4% (CoE 94.4%) | +2.1% |
| ComplexLP | **79.6%** | 52.1% | **+21.9%** |
| NLP4LP | 94.0% | 89.8% | +4.2% |
| ReSocratic | 88.7% | 81.0% | +7.7% |
| ComplexOR | 58.9% | 57.1% (CoE) | +1.8% |
| **Average** | — | — | **+7.7%** |

The more complex the dataset (ComplexLP / IndustryOR / ReSocratic), the larger the improvement. These are exactly the scenarios where solver-driven methods typically fail, indicating that semantic reverse verification captures the previously unmonitored "implicit semantic errors."

### Ablation Study

| Configuration | NL4OPT | IndustryOR | ComplexLP | NLP4LP | Description |
| :--- | :---: | :---: | :---: | :---: | :--- |
| **Ours (SAC-Opt)** | 86.8% | 63.8% | 79.6% | 94.0% | Full model |
| w/o correction | 82.9% | 50.5% | 63.8% | 90.1% | Removal of semantic anchor correction (Steps 3-5) |
| w/o debugging | 84.6% | 60.5% | 72.3% | 92.8% | Removal of solver error debugging (Step 6) |

**w/o correction leads to a much steeper drop than w/o debugging** (e.g., 15.8% drop on ComplexLP vs. 7.3%). This is the most crucial table in the paper, directly proving that "semantic correction" is the primary performance driver, while traditional "debugging based on error messages" is merely auxiliary.

Regarding Verifier comparison (Table 4): LLM-based achieves 86.8% vs. 83.1% for Similarity-based on NL4OPT; runtime is 78s for LLM vs. 157s for Similarity (Similarity takes more rounds due to coarser signals: 4.6 vs. 1.1 rounds on average). The Pearson correlation between the two verifiers across 7 datasets is 0.962, suggesting that the choice of verifier does not change the structural conclusions.

### Key Findings
*   **Semantic Correction >> Syntax Correction**: Removing semantic correction drops performance by 15.8% on ComplexLP, whereas removing debugging only drops it by 7.3%, proving the solver-driven paradigm misses the primary error source.
*   **Robust Across LLMs**: When using Qwen2.5-72B-Instruct, although absolute values are lower than GPT-4o, SAC-Opt still provides a stable gain of 4-9% over the w/o correction baseline (e.g., 57.5% → 62.9% on ComplexLP), indicating the gain stems from the mechanism itself.
*   **Greater Gains on Difficulty**: Improvements are 2-7% on simple datasets (EasyLP, NL4OPT) but are significantly amplified on complex datasets (ComplexLP +21.9%, IndustryOR +9.5%), where implicit semantic errors are more prevalent.
*   **Lightweight Verifiers are Viable**: The Similarity-based approach using `all-MiniLM-L6-v2` (no GPU required) still reaches 65.3% on ComplexLP, outperforming most baselines and showing that the "reconstruction + alignment" architecture is robust.

## Highlights & Insights
*   **"Back-translation" as a Self-Supervised Signal**: It essentially uses the expression discrepancy of the same LLM in two directions as a proxy for ground truth—requiring neither manual labeling nor solver feedback on correctness. If the forward and backward descriptions don't match, something is wrong. This logic is transferable to any "Natural Language → Structured Executor" task (SQL generation, API calls, tool use, agent planning).
*   **Fine-grained Incremental Correction Prevents Regression**: The Achilles' heel of traditional self-refine is that "regenerating code leads to fixing A but breaking B." SAC-Opt uses schema isomorphism to lock the correction scope to a single constraint/objective—an engineering-heavy but highly effective design.
*   **Terminable Convergence Guarantee**: Unlike many iterative LLM frameworks that rely on heuristic stopping criteria, SAC-Opt's convergence condition $\mathcal{E}^{(t)} = \emptyset$ is discrete, observable, and monotonically decreasing. Even with an imperfect verifier, the error set size is bounded.
*   **Simple/Semantic Separation is an Underrated Detail**: Moving $\mathcal{P}, \mathcal{V}$ to deterministic templates might seem like a small engineering detail, but it shrinks the correction state space from $O(|\mathcal{P}| + |\mathcal{V}| + |\mathcal{C}| + |\mathcal{O}|)$ back to $O(|\mathcal{C}| + |\mathcal{O}|)$, greatly improving efficiency and stability.

## Limitations & Future Work
*   **Reliance on Reliable Extract and Recons Agents**: If the `extract` agent extracts the original problem incorrectly (e.g., misses a constraint), the entire process verifies against a flawed ground truth. The paper does not address the propagation of extraction errors.
*   **Lack of Human Anchor-level Validation**: The authors note that the 0.962 correlation is dataset-level agreement, not anchor-level calibration against human labels. How accurate the semantic equivalence judgment actually is at the item level remains an open question.
*   **High LLM Call Costs**: Each iteration requires running `recons` + `verif` for up to $T_{\max} = 5$ rounds plus 3 debug rounds. A single problem takes 40-90 seconds (Table 4), which is 1-2 orders of magnitude more expensive than standard forward generation, presenting a significant cost for industrial deployment.
*   **Only Validated on LP/MILP**: All seven datasets involve Linear Programming or Mixed Integer Linear Programming. It has not been tested on non-linear programming, dynamic programming, or combinatorial optimization; as constraint languages become more complex, the ambiguity of the `recons` agent's descriptions may increase.

## Related Work & Insights
*   **vs. OptiMUS-0.3 (AhmadiTeshnizi et al., 2024a)**: OptiMUS performs correction at the extraction stage (fixing parameters/variables), but code stays solver-reliant. SAC-Opt pushes correction to the code semantic layer using back-reconstruction as a signal source, significantly outperforming OptiMUS (e.g., 79.6% vs. 52.1% on ComplexLP).
*   **vs. Reflexion (Shinn et al., 2023)**: Reflexion is a classic solver-driven feedback paradigm. SAC-Opt's critique hits the mark: solver feedback only covers "runtime errors" but is powerless against "runs correctly but means the wrong thing." The two can be stacked (and indeed, SAC-Opt step 6 is Reflexion-style syntax correction).
*   **vs. CoE (Xiao et al., 2024)**: CoE uses multiple agents but remains a forward one-shot generation process without a verification-correction loop. SAC-Opt is not just multi-agent; it introduces a reverse closed-loop, changing the focus from "division of labor" to "reconciliation."
*   **Broader Insight**: This "Forward Gen → Back Recons → Itemized Alignment → Selective Correction" template applies to all "NL → DSL/code" tasks—SQL generation, JSON schema extraction, function calling, etc.—and can be implemented as a self-correction framework without additional training.

## Rating
*   **Novelty**: ⭐⭐⭐⭐ Using reverse semantic reconstruction for self-correction is explicitly proposed here for the first time in this track.
*   **Experimental Thoroughness**: ⭐⭐⭐⭐ 7 datasets + ablation + cross-LLM + Verifier comparison + Case Studies are all provided; missing only anchor-level human calibration.
*   **Writing Quality**: ⭐⭐⭐⭐ Algorithm 1 and the inverse loop diagram are clear; the motivation regarding "silent semantic errors" is well-articulated.
*   **Value**: ⭐⭐⭐⭐ The pattern is transferable to the entire NL→DSL family and is training-free for engineering use, with significant potential impact.
